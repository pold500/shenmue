Shenmue Scene Decompiler

scn_decomp.py turns Shenmue I scenario bytecode (.scn, SCN3) into plain C. scn_compile.py compiles edited C back to .scn. scn_studio.py puts both in one window: a Decompiler tab and a Compiler tab. Everything needs only a uv-managed Python, with no extra packages.

How to run

GUI

Double-click scn_studio.cmd, or run this from build/qa/tools:

uv run --no-project --python-preference only-managed python scn_studio.py

Command line

# every scene in scn/ → out/scn_c/, about 80 seconds
uv run --no-project --python-preference only-managed python scn_decomp.py all

# one scene, a couple of seconds (engine signatures come from scn_api.json of an 'all' run)
uv run --no-project --python-preference only-managed python scn_decomp.py scene scn\act02_d000.scn
all

Optional arguments: the folder with .scn files and the output folder. Writes a .c and a .json per scene, a shared scn.h, scn_api.json and report.txt with the clang check results.

scene

Path to one .scn and an optional output folder. Without scn_api.json, engine signatures are inferred from that scene alone.

How the decompiler works

  1. Decode. scn.py reads the .scn header and decodes the instructions. Function boundaries come from calls, thread starts, event tables and add sp prologues.

  2. Control-flow graph. Each function is split into basic blocks at jz, jmp and ret.

    Unreachable code is dropped: dead jumps left by the original compiler and 0xff padding bytes.

  3. Symbolic execution. The VM stack is modelled with expression trees: push adds a value, an ALU operation combines two values into an expression, a call takes its arguments.

    Access widths (s8/s16/s32), comparison results of −1/0 and the value of an assignment follow SCN_Parse. A stack value that could otherwise be evaluated out of order is moved into a temporary tN. An accumulator value that crosses blocks becomes the variable acc.

  4. Structuring. Back edges become for, while and do; forward conditional jumps become if/else; exits become break, continue and return.

    Whatever does not fit these shapes stays a plain C goto.

  5. Type inference. Evidence is collected across all scenes: float operations vote for float, masks and shifts for int, taking an address and dereferencing for a pointer. The majority wins.

    Where a script really reads the bits of one type as another, an explicit as_float/as_int is written.

  6. C output. Prototypes, workspace globals, the data segment as C arrays in file order, and the function bodies.

    A JSON file next to each scene stores per-function hashes of the bytecode and of the C text. The future compiler will use them to copy unchanged functions byte for byte.

  7. Check. The all mode runs every file through the clang that ships with Visual Studio (-fsyntax-only -std=c17) and writes the result to report.txt.

Dialect rules

The code is plain C, with a few conventions the future compiler relies on. The full description is at the top of scn.h.

local_1c

The frame slot at fp − 0x1c. argN is the argument at fp + 8 + 4N.

ws_10, ws2_99f

Offsets in the scenario workspace. ws2 starts at ws + 0x100.

str_45b97

The data object at that offset in the file: str_, vec_, tab_, events_, bin_.

FOURCC('JIMY')

The 32-bit ID whose bytes in memory are J, I, M, Y.

as_float(x)

The same bits read as the other type. The casts (float) and (int) convert the value.

-(a == b)

A VM comparison yields −1 or 0, so where the result is used as a number it gets a minus.

Say(text)

The dedicated string opcode 0x08, which shows a subtitle.

F_GMCT_ROUTE_STARTED

Flag names from script_catalogue.def in calls to Script_scenUtils(11/12, …).

Evaluation order

Operands are evaluated left to right, call arguments right to left. Integers are 32-bit and wrap around.

Limitations

  • Behaviour has not been checked against the bytecode yet. clang checks syntax and types. An equivalence check will come with the C → .scn compiler and a VM emulator.
  • Types are inferred heuristically. In places the class may be wrong, which shows up as an extra as_int or cast.
  • Expected under C rules and not counted as findings: int/pointer casts, & between comparisons, reads of uninitialised locals (as in the original scripts), K&R definitions, and Japanese strings that are longer in UTF-8 than in cp932.
  • 100 of the remaining clang warnings are -Wreturn-stack-address: by its name, functions returning the address of a local. These have not been reviewed.
  • Names are address-based (fn_33ab9, local_10). Human-readable names will come with the VS Code extension.
